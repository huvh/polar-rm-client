# 旧图传解码延迟优化（2026-10-22）

参考 `D:\StandardRobot++\Pacific_doorlock_sniper\src\doorlock_decoder\doorlock_decoder\video_decoder_node.py`
中的 `CodecContext.parse -> decode -> to_ndarray(bgr24)` 实现。仅迁移终端需要的连续解码链路，
不引入 ROS、参考项目的 3000 深度 QoS、FRAME 帧线程或显示队列，也不修改接收端网络配置。

## 最终链路

旧图传 UDP/官方桥接入口 → 原有 Annex-B 参数集恢复 → 有界输入队列 → 单线程 PyAV H.264
解码 → 最新 BGR 图像槽 → 原有 HUD。取消中间的 JPEG 编码、输出管道与 OpenCV JPEG 解码。
`low_delay` 和 `showall` 保留旧接收端循环帧内刷新、无 IDR 码流的兼容性。

- 输入队列容量 128 个块；运行中待处理块超过 50 ms 时撤销整个解码会话，沿原有恢复流程
  等待新的参数集与可恢复首 slice。250 ms 启动宽限用于容纳进程兼容路径的首个 GOP。
  这只限制应用输入排队时间，不是端到端延迟上限。
- 不任意丢弃单个 H.264 分片后继续拼接参考帧。队列满同样撤销当前会话。
- 停止先撤销代际，等待解码线程退出后才释放 CodecContext；旧线程不能发布到新画面槽。
- 普通 H.264/H.265 入口继续使用原 FFmpeg 解码路径。缺少或无法初始化 PyAV 时，旧图传
  也保留 FFmpeg 兼容回退；`h265_decoder_health.native_decoder_error` 提供回退原因。
- 生效标识为 `decoder_backend=pyav-bgr`。依赖 `av>=14` 已加入两份运行依赖和 PyInstaller
  收集列表。本次验证只在临时目录加载 PyAV 18.1.0，没有更改项目虚拟环境。

## 本地对比

运行 `tools/video/benchmark_decode.py`，同一条 1280×720、60 FPS、180 帧 H.264
测试码流，按原速投递，保持输入管道开启。基线保留原有单线程和低延迟参数，仅使用原先
JPEG 中转方式。起点是解码器 `start()` 返回后的数据投递时刻，终点是 BGR 图像发布，
不包含首次导入依赖、采集、无线传输、UDP 接收或屏幕显示；单次测量不代表现场端到端结果。

| 指标 | FFmpeg/JPEG 基线 | PyAV/BGR |
| --- | ---: | ---: |
| 首帧投递到发布 | 73.91 ms | 24.61 ms |
| 稳态延迟中位数（前 15 帧除外） | 23.75 ms | 20.71 ms |
| 稳态 P95 | 24.43 ms | 21.77 ms |
| 解码帧数 / 投递帧数 | 179 / 180 | 179 / 180 |
| 输入丢块数 | 0 | 0 |

最后一帧尚未收到后续边界，留在 Annex-B parser 中；没有用关闭 stdin 或 flush 的方式
把离线尾帧算作在线低延迟。原始结果见 [测量报告](../../reports/video/legacy_video_latency_20261022.json)。
